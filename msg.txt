Send only the host's files while a workspace is connected

Follow-up to the SimpleRemote lifecycle work: four holes an adversarial
review of that commit found, three of them in code that was written to be
defensive and was not.

Local buffers.  While a workspace is connected the daemon launches every
language server on the host, but BufferServable() only gated remote://
names, so an ordinary local buffer -- :e ~/scratch.py, a dotfile, another
project -- was still sent, text and all, to a server that cannot resolve it.
The damage came back through the URI mapping: UriToPath() maps every file://
a connected server sends to the host's namespace, so the definition or
diagnostic that server answered with for file:///home/…/scratch.py became
remote:///home/…/scratch.py, and `gd` inside the buffer the user was already
in fetched an unrelated path from the host instead of moving the cursor.
Only the host's files are offered now: a remote:// buffer of this
connection, or, in a projected mode, a file under local_root, which is the
same file seen through the mount.  Everything else waits for the
disconnect, whose restart replays it to the local servers.  :SimpleCCHealth
says so in CONTEXT rather than leaving "document: never opened on the
server" as the only clue.

Probe values.  EffectivePythonSelection() assigned an untyped probe value
into a string variable and only then checked its type, so a probe entry
that was not a string threw E1012 from the line above the guard -- and,
since SendInitialize() calls it, would have aborted initialize and left the
daemon permanently not ready.  HealthRemote() compared the same untyped
values with ==# and threw E1030.  Both read through ProbeString() now, which
is what the report's own probe-detail loop already did.

Probe timing.  SimpleRemote seeds the in-flight probe as {status: -1} the
moment it starts the process, so empty(probe) never described "still
running": :SimpleCCHealth in the first second after connecting reported
"remote python: (none found)" with a hint about the remote PATH, while
"runtime probe: not run yet" was reserved for users with no runtime
installed at all -- the opposite of what its :SimpleRemoteProbe hint
suggests.  ProbePending() treats a probe carrying nothing but a negative
status as unanswered.

Hierarchy lists.  The call- and type-hierarchy quickfix producers never got
the user_data the other lists carry, so QfEnter() had to reinterpret their
byte column as a UTF-16 offset.  Their columns are built while the target
buffer is loaded, so they are real byte columns, and a buffer that is
dropped and re-read before <CR> landed the cursor well past the symbol.  All
three producers are one HierarchyToQuickfix() now, carrying the LSP column
and binding SimpleCC's <CR> like every other list -- which is also what lets
them wait for a remote:// buffer to be filled.

test/remote_paths.vim covers what a connected workspace will and will not
send in both modes and the probe fallbacks; test/remote_lifecycle.vim opens
a local file against the simulated host and watches it stay unsent until the
disconnect, then jumps through an incoming-calls entry whose buffer was
unloaded after the list was built; test/health_doctor.vim asserts the REMOTE
section for a pending probe, a garbage probe and a real one.
